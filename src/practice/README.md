# 练习记录

## 2026-09-08：工具片段组装（02.ts）

### 目标与结果

输入是一个固定的片段数组。同一个工具的片段可能与其他工具交错出现，需要按 index 分组，保留 id、name，拼接 arguments 字符串，解析并返回完整工具数组。

已完成主要逻辑。验证通过：类型检查、两个工具交错拼接、保留字符串中的空格、处理字符串里的右大括号，以及拒绝不完整 JSON、非法尾部和数组参数。

最后一次检查时，非法 JSON 已经会抛错，但错误文本仍是 `invalid json`；已建议补上工具 index，尚未复查这一行。

### 主要感受：JS 写法与 TS 结合后，复杂度明显增加

这次主要的负担不只是分组和拼接，而是：以前熟悉的 JS 编码习惯，为了配合类型检查，需要重新组织。除了考虑“代码运行时怎么做”，还要考虑“类型系统能不能确认数据已经准备好了”。两件事一起学习，增加了理解成本。

具体表现：

- 习惯先建空对象再逐项赋值，但 `{} as Tool` 提前声明它已经完整，与后面判断字段不存在的逻辑冲突。
- 改成 `Partial<Tool>` 后，能表示组装中的状态，却不能直接放进要求完整结果的 `Tool[]`，还需要确认字段齐全。
- Map 补上键和值的类型后，读取结果还需要考虑不存在的情况。
- JSON 能成功解析，不等于解析结果符合工具参数的对象结构；接成 unknown 后，还需要验证才能使用。

这些成本是真实的。但不必把每次报错都解决成更复杂的类型技巧：这题用局部变量收集，最后检查并一次性构造完整 Tool，就比围绕空对象不断补类型更直接。Partial 本身没有错，只是本题不必使用它。

### 这次整理出的类型习惯

- 输入 Fragment 如实允许 id、name 缺失；最终 Tool 保持必要字段必填。
- 分组使用 `Map<number, Fragment[]>`，让遍历变量自动获得类型。
- 收集中尚未获得的 id、name 用 `string | undefined` 表达；content 从空字符串开始，让 TS 推断。
- 在组装结束处集中检查必要字段，再构造完整结果。
- 解析参数先接成 unknown，确认是非 null、非数组的对象；这只验证对象形状，还没有验证具体工具要求的 path 等字段。
- 不以消除红线为目的滥用 as，也不把所有字段改成可选。遇到报错，先检查类型声明是否符合数据当前的状态。

参考：[TypeScript 可选属性](https://www.typescriptlang.org/docs/handbook/2/everyday-types.html#optional-properties)、[类型收窄](https://www.typescriptlang.org/docs/handbook/2/narrowing.html)、[Partial](https://www.typescriptlang.org/docs/handbook/utility-types.html#partialtype)。

### 与类型无关的逻辑问题

- 后续片段缺少 id、name 时，不应覆盖之前已收集的值。
- 拼接片段不能随意 trim，否则会删除 JSON 字符串中的有效空格。
- 固定数组已经包含全部片段，应在一组遍历结束后解析一次，不用寻找右大括号来猜测 JSON 是否完整。
- 解析失败应抛错，不能只打印后继续返回旧结果。

### 后续学习节奏

本题难度目前刚好：范围小，有明确输入和输出，需要独立组织逻辑，又能直接验证结果。

保持用户先写、再按实际代码评审的方式；每次集中处理一两处问题，不在一次修改中连续引入过多类型概念。说明时同时展示“当前数据是什么”和“这一步变成什么”。验证完成即收束，不不断追加要求。

## 下次：文本消息切割

今天到此结束，下次再开始。

使用固定字符串数组模拟分块接收，只练习切出完整消息，并保留未完成尾部等待下一块。不接真实 fetch，不解析 JSON，不处理工具调用；先只支持 `\n\n` 分隔符。

输入示例：

```typescript
const chunks = [
  'data: {"text":"你',
  '好"}\n\ndata: {"text":',
  '"世界"}\n\n',
];
```

期望输出：

```typescript
[
  'data: {"text":"你好"}',
  'data: {"text":"世界"}',
]
```

核心新点只有一个：当前片段不完整时保留它，等下一块接上。开始练习时先明确完成标准，再由用户自行实现。
